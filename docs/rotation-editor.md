# Rotation editor

Import/Export has three actions that are easy to confuse. With Replace selected entry ticked, the first button reads **Compare import** and shows what would change in the selected rotation. For a new named copy it reads **Preview import** and opens everything the import contains in the same read-only view a Built In has (header, specializations, switch condition, steps and cooldowns); it saves nothing. **Check import** is different: it lists problems with the text, such as why it cannot be imported and any unsupported data.

Open `/rm config` and select Rotations. Default and custom rotations share the same view. Defaults are read-only: inspect their cards and conditions, enable or disable them, or use Clone to edit. A clone is independent and keeps its original source for comparison.

Custom rotations use a private draft. Apply saves the draft; Discard restores the saved rotation. Undo and Redo step through structural, field and condition edits. Closing the window keeps the draft available during this session. Apply before `/reload` or logout to retain edits across sessions. Switching rotations or opening comparison/transfer while a draft is dirty offers Apply, Discard or Cancel.

The header is two rows. The first is the specialization picker, the name field (it has no label; empty, it reads "Name") and Metadata. The second starts with one fixed slot: the blue Read-Only pill on a Built In, or Undo and Redo (icon buttons with tooltips, together as wide as the pill) on your own rotations and the Default, so nothing moves between them, and the rest of the row is flush right, in one order: ID, Priority, Enabled, Delete. Those four sit at the same coordinates on a Built In and on your own rotation. Reset to default (a Built In whose settings you changed) goes to the left of ID in the free space, so it appears without moving anything; at the minimum window width, where there is no room beside ID, it takes the line below, flush right. The cluster fits one line beside the slot at the minimum window width in the shipped languages; where it cannot (a very long translation or a very narrow pane) it drops whole to the next line, still flush right. Controls never overlap. Metadata opens a form with a larger description box and optional Author, Realm, Email, Website and Version fields. Enable/disable and Delete are docked at the right. New rotation, Duplicate, Import/Export and Compare rotations live in a two-row grid below the rotation roster. Use changes stages metadata and description together as one undoable draft edit; the rotation’s Apply button saves them. Cancel or Escape abandons form edits. Defaults show the same form read-only. Retained source titles and links stay separate; contact fields are never filled automatically. Deleting a whole custom rotation requires confirmation and cannot be undone; deleting a card in a draft can be undone. Defaults and the implicit fallback rotation cannot be deleted. A new rotation that was never saved needs no confirmation to throw away: Discard, the header Delete and the unsaved-changes prompt's Discard remove it from the list, and so does choosing another rotation or closing the window while it is untouched.

The switch condition appears below the toolbar as a clickable summary. Click its text to open its condition tree; click the heading to hide or show that summary. Opening an untouched fallback or read-only default does not create unsaved changes. The fallback rotation is selected when no other rotation matches and has no editable switch condition.

## Specializations

A rotation's specializations are its own setting, `body.specs`, edited with the picker that leads the header, before the name (several, or Any; read-only on a Built In, absent on the fallback). Absent or empty means any specialization. It decides where the rotation is listed: the Rotations list, the minimap menu, `/rm set` and `/rm list` offer it only while you play one of them, and a refusal says "it is for another specialization" (`/rm why` names which). The switch condition never decides that: it only drives automatic switching, which checks the specialization first, then the switch condition, then priority. A rotation with no switch condition (none, an empty one, or a tree with nothing in it) matches whenever its specialization, level, edition and action bar allow it, so priority alone ranks it among everything else that matches; the shipped premades with nothing to test have no switch at all. To keep one for choosing by hand, turn it off (Enabled). A tree that is not empty but broken (an unknown condition) is not "no switch": it fails validation and the rotation cannot be selected. The editor's switch pane says so when it is empty, and `/rm list` and `/rm why` no longer have a "manual only" state. Saved rotations that had an empty switch were manual only before and now match automatically (the Default fallback is unchanged: the last resort).

The specialization menu heads the list column, above the search box (no row is added between the tabs and the panes). It starts at the specialization you are playing on every opening and after a respec, lists the class's specializations (and Retail's "No specialization") and All specializations, and shows "This is not your current specialization." under it when another is chosen. Rows for other specializations are hidden like another class's; rows for any specialization always show. A new rotation is for the specialization the menu shows (Any under All). Each specialization has its own fallback (Default), kept under its key: the list shows the Default of the specialization it is set to, and All specializations lists every specialization's Default, each named by its specialization (Retail's "No specialization" has its own), selectable and editable in its own namespace. Only the Default of the specialization you are playing is ever used; the others are for viewing and editing.

What a value means is a fact of the client (`Platform/specializations.lua` `GetRotationSpecKind`): Retail and Mists of Pandaria Classic use the game's specialization IDs, which mean the same on every account and travel in exports. Classic Era and Season of Discovery, TBC, Wrath, Cataclysm and Forever use the talent group (primary or secondary talents, or the name you gave it in General), whatever the character's level or whether dual specialization is unlocked: a talent group means nothing on another character, so exports leave `specs` out and an import is for the talent group the list shows (your current one under All); re-importing over a rotation keeps its own. A rotation for only another class's specializations is refused on import like any other class mismatch.

Rotations saved before this setting existed were moved once per profile (`rotationSpecsMigrated`): where the saved namespace is a specialization value (Retail, Wrath and Cataclysm) a rotation got that value, and where `SPECIALIZATION` reads a specialization ID (Retail, Mists) a switch that is exactly `SPECIALIZATION`, an OR of only `SPECIALIZATION`, or an AND with one `SPECIALIZATION` child lost that part to `body.specs`; a switch left with nothing is left empty, which now matches whenever the rotation applies, so it still chooses itself. (Profiles migrated by the build that briefly used `LEVEL >= 1` for this keep that harmless always-true condition.) Anything else stays an ordinary condition.

## Footer and selection

The footer is one row of controls anchored to one another: Discard at the right edge, Apply, View Changes, then (while cards are selected) the selection bar, and the hint or status text in whatever is left. Buttons are as wide as their text, so long translations push their neighbors over instead of overlapping them. When the row cannot hold the selection bar and a readable hint (a long translation at the minimum window width), the bar takes a row of its own above the buttons and the canvas gives way. Clicking a card of your own rotation selects it (gold outline, "N selected"); opening a rotation never starts with a selection. A Built In cannot be edited, so selection has no purpose there: clicking its cards never selects them, never draws the outline and never shows the selection bar (the chevron and the action text still expand and collapse a card).

Blizzard's suggestion card wears the icon of Blizzard's one-button assistant (the spell Single-Button Assistant, 1229376; the icon is read from the client, with the condition icon as the fallback on a client without it). Stop has its own icon, `Assets/Conditions/stop`, whatever its condition checks. The suggestion card's amber warning says how many of the spells Blizzard can suggest are on no action bar; those are skipped only when Blizzard actually suggests one, and the card works for the rest.

## Independent cooldowns

Cooldown cards appear above the ordered rotation in a responsive grid. Each block heading can collapse its entire block into one row; the editing buttons are replaced by a Click to expand hint while hidden. Expand all and Collapse all control the cards, followed by the Add buttons. Cooldowns have no ordering arrows. They can all highlight independently when their conditions are met. Their visual position does not impose a sequence. Add cooldown creates a new reminder; drag the control into an insertion gap to choose its place.

The chevron toggles Summary and Name only. Click action text to replace the action summary with fields while retaining the editable condition below them; the double-down chevron returns from fields to Summary. In the condition editor, click condition description text for fields. Name-only cards retain drag and expansion. Collapse all keeps branch paths visible; the separate branch-path icon folds a subtree when desired. Expand all restores summaries and paths. Mode/enable pills sit beside Help on the top row. Cooldown summaries show the effect on their spell icon; action details keep that leading spell icon as their live preview. Use this exact spell rank is a checkbox on every spell, cast, channel, aura and announcement rank option, unticked by default, and absent on clients without spell ranks. Labels sit to the left of fields and center vertically against their controls, magnification uses a numbered slider, and the direction pad adjusts numeric offsets (Shift moves ten pixels), and Center resets to CENTER/0/0. A color swatch opens an owned HSV/alpha picker with live draft preview; RGBA inputs use two rows beside a swatch spanning both rows. Channels accept decimal values from 0 to 1. Offset values are stacked beside the directional pad; Default resets return the corresponding settings to the profile. Cancel restores the previous pending values, including unfinished input. Sounds come from LibSharedMedia with a play preview. Blank optional overrides inherit the profile settings.

## Ordered actions and branches

Add action appends an action; drag it into a gap to insert elsewhere. Click a plain-text card name to rename it in place; the input replaces the label at the same position, and clicking outside finishes editing within the draft. Click its action to change action fields, or click the condition summary to inspect/edit its guard. Spell identities support hover tooltips; Shift-click an action to open its spell link. Selected spells keep their icons in action details. Actions implicitly require the learned spell or carried item, readiness, resources and valid range.

Add branch creates a conditional decision. Drag Add branch into a gap to put it before existing steps. Inserting a branch moves all following siblings into its True arm. False is on the left with red connectors; True is on the right with green connectors. An evaluated branch has a white border. Its mode pill cycles through Evaluate condition, Always true and Always false. Forced modes skip guard evaluation; cards in an unreachable arm are gray.

Dragging an ordered card into a different branch arm carries the rest of its source sequence with it, including every nested branch subtree. A destination inside any carried subtree is refused. Moving within the same sequence or using Up/Down reorders the selected card and its own nested subtree. Cooldowns remain independent.

A branch finishes its selected arm and then rejoins any siblings following that branch. Stop ends the ordered sequence; the implicit auto-attack (Attack or Shoot) may still apply unless the Stop explicitly suppresses it. Attack is recommended in melee range; beyond it, Auto Shot or wand Shoot when the target is in its range and that button is on the action bars. Independent cooldowns continue to be evaluated.

Undo reverses an insertion, captured tail or grouped move as one edit. Apply validates both arms, including currently unreachable cards, without running custom condition code. Incomplete or unavailable cards have red borders and remain editable when validation refuses Apply. A warning above the switch condition explains why the rotation cannot run; click it for diagnostics.

Dragging displays a floating card preview beside the pointer and highlights one valid insertion gap. A drag release does not also activate the source button. Both axes scroll when needed. RM positions and drags its own scrollbar thumbs so downward/rightward motion always increases the scroll offset. Thumbs reflect how much of the content is visible; click empty track space to page in that direction, or use the wheel or small arrows for smaller movements. Window scaling applies on slider release and also reaches RM child windows.

In the condition editor, Add condition and Add group append to the whole expression’s end regardless of the selected card; drag either button into a gap to choose a nested position. All/Any pills are yellow. Disabled cards retain their condition descriptions in gray, and icon-only controls have no button backgrounds. Empty rotation branch arms keep their colored path continuous.

Collapsed section hints are clickable, including Switch condition. Compact unnamed conditions show their readable summary; clicking a compact title opens Summary. Named steps supply the condition editor title. Generated action titles omit hyperlink brackets while actionable spell descriptions retain tooltips/links. Disabled card summaries keep their ordinary wording. The condition dialog shares the main window’s dark chrome, compact single-row contextual header and footer.

Apply clears highlights using the previously saved action identities before evaluating the new settings, so changing an effect does not require switching rotations. Textured overlays inherit their target’s frame strata and sit one level above its icon, including in configuration dialogs.

Leaf and grouped conditions initially open at Summary; click condition text to show field controls. Noninteractive condition-edit buttons and compact card titles use plain spell names without hyperlink brackets. Actual spell links in the condition editor retain their link behavior. Card hover guidance is rebound on every render. Metadata opens at the workbench dialog layer and uses the standard RM Escape handling, including clients without the special-frame registry.

The condition editor uses a single-row header. Its heading is “Rotation Master: <step name>”, including an unfinished rename or the displayed spell/action name. The right side identifies Rotation, Cooldown or Switch condition; the footer shows the rotation name left aligned. Metadata uses matching chrome with a Metadata context label.

Metadata sits to the right of the rotation name, above Enabled/Delete. Its description is a multiline scrolling field; the dialog grows for actual source information and omits that section when absent. Use changes stages details in the rotation draft; Cancel/Escape restores the dialog’s opening values. Apply the rotation to save.

Up/Down controls are disabled at each sibling list boundary, including inside branches and condition groups. Group arrows remain on the left; the child connector starts below them and keeps its horizontal arms. Split group sits between Duplicate and Delete on the right. Compact unnamed condition groups show All of/Any of; named groups keep their name.

## Tags and search

Metadata includes a comma-separated Tags field. Any personal labels are supported, including tags such as AOE, PVP, Raid or MyLittlePony; quote a tag containing a comma and double any quote inside it. Empty text removes all tags. Up to 64 tags of 64 UTF-8 characters each are supported. Duplicate tags use the first spelling and compare without ASCII case differences. Tags are metadata and do not change switch conditions or recommendations.

Defaults show their tags read-only. Clones and imports inherit manifest tags unless their editable body explicitly supplies tags; an empty body list suppresses inheritance. Editing tags participates in the rotation draft, Apply/Discard and Undo/Redo. Cancel in Metadata restores its opening values. Leaving an inherited value unchanged keeps it absent from the body, so merely viewing or confirming a clone does not create a difference. Exporting an edited sourced rotation reflects its current tags without changing historical source records.

The roster has a searchable tag filter alongside All/Defaults/Custom ownership filtering. The existing search box matches name, description, tags, provided author/realm/contact/version metadata and source citation titles/URLs. No player or contact information is filled automatically. Filters combine without changing or discarding the selected editor. New clears active filters so its pending entry is visible. Tag changes have a readable side-by-side row in rotation comparisons.

## Auto-switch priority

Metadata includes Switch priority, a whole number from -100000 to 100000. Larger numbers win among custom rotations or among packaged defaults. Missing/blank priority means zero. Equal priorities use name, then stable identity, so equal names no longer depend on table iteration order. The roster shows each candidate’s priority; the saved fallback has no competing rank.

Custom rotations retain precedence over packaged defaults, and a valid saved fallback still takes precedence over a packaged recommendation. Priority does not override applicability, disabled state, invalid conditions, manual selection or the Disable auto-switching setting. Invalid priority makes a body unavailable to automatic selection. Metadata edits stay private until Apply and are undoable. The graphical diff shows priority changes. Existing rotations without priority retain their alphabetical behavior. This introduces explicit precedence without running additional condition callbacks to detect simultaneous matches.

`/rm check` reports invalid saved priorities without changing them. Explicit `/rm repair` clears a malformed priority back to the implicit zero, including on branch-based rotations. Graphical comparisons treat absent and explicit zero as equal; the diagnostic raw diff preserves their storage difference.

## Aura ranks

Buff/debuff presence, time and stack predicates offer Use this exact spell rank, like every other rank option, on clients that have spell ranks (Era, TBC, Wrath, Forever); Retail and Mists show no rank checkbox anywhere. A new aura condition starts unticked, so any rank matches; the stored field `anyrank` is true then. Conditions saved without it keep matching the exact numeric spell ID and show the option ticked. Unticked also matches a readable aura name against the authored ID’s readable localized spell name. Named legacy aura predicates retain their existing name matching. Aura pickers preserve numeric selections so disabling the option does not silently keep name-family behavior. No raw spell IDs are needed in the displayed search or icon.

Missing metadata and restricted identity are unavailable, including under NOT. An observed empty aura list remains ordinary absence. Different spells with the same localized name can match in family mode; use exact IDs when the distinction matters. Own-aura filtering and time/stack behavior are unchanged. Built-in condition checkboxes now use RM’s flat control through a shared layout adapter; RM owns ordinary field layout and widget leases; Native List, Table and RM-SpellField layouts replace the retired GUI compatibility path; older custom widgets must adapt.

Built-in condition text and numeric inputs also use RM's flat controls. Sliders have an editable number beside the track. Percent fields display 0–100% while storing the original 0–1 fraction; opening a field never rounds its saved value. Dragging or wheeling uses the configured step, while typed values can retain finer precision. Enter or leaving the field confirms an edit; Escape restores its last confirmed value. Apply, Undo and changes to the card layout collect pending input first. Invalid slider text stays red and blocks application until corrected or canceled. Explicit legacy custom widgets and advanced layouts retain their compatibility bridge.

## Classic talent trees

Primary Talent Tree selects the unique Classic talent tree with the most positive points. Talent Tree Points compares the points in a selected tree and can explicitly test zero. Both use readable player metadata from the existing tree adapter. They do not interpret the saved rotation slot as a major spec.

No spent points, tied positive maxima or incomplete/unreadable tree metadata cannot establish a primary tree; that condition is unavailable, including under NOT. Tier-grid and trait layouts are unsupported by these tree predicates. New-profile defaults place the conditions in Character and allow them in switch conditions; existing custom category/switch lists are preserved and can be adjusted in Conditions management. Hybrid builds can combine tree-point and individual-talent predicates rather than treating a primary tree as a role assignment. References remain inspectable on unsupported clients. These are authoring primitives; they do not add later-level or other-class default packs.

**Trees are named, never numbered.** The conditions save a tree as its position in the talent window (1, 2 or 3), because that is what the game's talent calls take and what a rotation carries between characters; people see only names ("Elemental", "Enhancement", "Restoration"). Every place a tree appears (the Talent Tree pickers of Primary Talent Tree, Talent Tree Points and the Classic Talent condition, the condition summaries and cards, the tooltips and help) resolves it through `addon.TalentTrees` (`Data/talent_trees.lua`): for the class the rotation is for, a class the player is playing takes the game's own names (`Platform:GetTalentTreeInfo`, in the client's language), each missing one from the table; any other class, and a client whose talent data has not loaded, takes the shipped table. The table has one list of three names per class for each client family (Era and Season of Discovery, TBC, Wrath, Cataclysm, Forever), in talent-window order, and its names are translated through the locale files (`TalentTree.<English name>` keys, not the plain spec-name keys, which also name creature types and spell schools). "The class the rotation is for" is the class of the rotation open in the Rotations editor (`workspace:RotationClass()`: a saved rotation's owner class, a Built In's declared class), else the player's. `tests/talent_trees.lua` fails when a Built In premade's tree number names a different tree than the premade is for. `python3 tools/export_talent_trees.py` writes `Data/talent_trees.json`, the same table for the website (`--check` is part of `tests/test_talent_trees.py`). A tree-layout Talent condition names another class's tree but not its talents (the game cannot be asked), so such a talent reads `<talent>`.

## The Talent condition's picker

On every client the Talent condition's picker is one block: the talent's icon on the left, as tall as the two lists beside it (a question mark until a talent is chosen), the upper list above the Talent list. Retail's upper list is the Specialization (the rotation's own, defaulting to the one played; the others of your class are read outside combat) and its Talent list is grouped under headings for the class, specialization and hero talents, with each choice of a choice node listed; Forever and the Classic clients with trees put the Talent Tree above the tree's talents; Mists puts the Tier (with its level) above the tier's three talents. Choosing writes the same fields as before: a tree and talent number, a Mists slot, or a trait node, entry and spell. "Show talent tree" (Retail, Forever) sits beside the Talent list when the pane is wide enough, else under the lists, and is off while the lists could not be filled. `/rm debug talents` reports why a Retail or Forever list is short or empty (docs/talent-selector.md section 2).

## Large rotation workspaces

Rotation geometry retains every visible node allowed by the shared body validator (at most2,000 total steps and16 branch levels). Folding a branch or arm still intentionally hides its descendants. The former independent first200-card display truncation has been removed. In scenes above200 visible cards, rich native card controls are pooled around the current viewport, with overscan, while complete branch geometry and insertion targets remain available. Diagram zoom/pan and ordinary list/cooldown scrolling use their own saved viewport coordinates.

Reused cards keep detached pending edits and receive fresh callback ownership. Focused name/field inputs and floating drag sources remain attached until editing or dragging ends; panning and drag-scrolling populate newly exposed cards. Measured fields update scene heights when first materialized. This reduces control allocation; connector, group and insertion primitives still represent the complete scene. It does not promise unlimited or constant-cost rendering. The separate condition editor now also retains complete geometry for its supported4,096-node model, with viewport pools for cards, connectors and insertion markers. The portable data/depth limits still apply. Focused/pending field panes and active child editors remain leased while offscreen, and stale handlers cannot edit a recycled card. Its readable description has an independent bounded-text limit; the copy button describes that bounded report rather than promising the entire expression. Synthetic large-scene fixtures cover geometry, navigation, pool reuse, edit retention and drag lifetime; native WoW performance/interaction acceptance remains pending.


## Custom condition field requirements

Root fields in the graphical schema editor have a Required checkbox. It stages whether that field must have a value for the condition to run. Renaming, reordering and duplicating a root field carry its requirement; deleting it removes the requirement. Moving a root field into a nested record clears its root-only requirement, and Undo restores the prior metadata. Child Apply stages fields, order and requirements together; the condition's Apply saves them. Callback Lua code is never rewritten.

Advanced schema edits remove requirements for names explicitly removed from the schema once that edit is successfully committed. They do not infer a rename. Invalid imported requirement references remain visible as invalid metadata until the graphical schema is explicitly applied; its review message explains that only displayed root requirements are kept. Required-only changes mark the schema viewport and expire prior Test setup. The schema editor now keeps complete root/nested geometry and pools nearby rows, ancestor cards and drop gaps. Focused or dirty fields remain leased while offscreen. Every supported field remains reachable, including compatibility data that must be reduced before a new graphical snapshot can be applied. Schema validation and baseline markers are indexed per revision; scrolling does not rescan every sibling pair. Toolbar and footer controls remain outside the scroll child. Advanced allows64KiB of input with unchanged512-node/16-level parsing limits; untouched compatibility schemas validate from their stored model instead of being reparsed through those new-input limits.

The header's specialization picker is on every rotation. On your own rotation it chooses the specializations; on a Built In it shows them, read-only; on the fallback (Default) it shows, read-only, the specialization that Default belongs to, named as the list's specialization menu names it ("No specialization", a talent group, or "All specializations" where one Default serves every specialization).

Each row of the rotation list is one line: the kind (Built In, Custom or Fallback), the specialization (Any specialization when it applies to all) and the priority (a fallback has none). When the specializations are too long for the column they give way; the kind and the priority are never cut. Read-only, switched off, overlaps and unavailability are the row's color, order and tooltip, not words in the line; `/rm list` keeps its statuses.

The "not on your action bars" warning on a card reads the last action bar scan. Nothing is judged before a scan has run or while a bar change waits for its rescan, and opening the editor rescans an old index. A spell the bar holds under another ID still counts: the base and override spells the client relates to it, the slots the client itself reports for it, and (on Retail) a spell of the same name, which is how a specialization's version of an ability (Brewmaster's Blackout Kick, 205523, and the class one, 100784) matches. `/rm debug glow` has a section listing each unbound step's spell IDs, their relatives, how each was looked up and what the scan holds.

In a card's effect fields and on the General page, the Horizontal and Vertical offsets (H and V; the tooltips give the full names) sit side by side, splitting the row beside the position pad 50/50.
