Source snapshots and revision IDs are in client-api-sources.json. Forever's product-specific file is [Blizzard_ProjectConstants/Camelot/ProjectConstants.lua](https://github.com/Gethe/wow-ui-source/blob/172a387e3ab85b26e6640d3058d5ec1e6ccd4c63/Interface/AddOns/Blizzard_ProjectConstants/Camelot/ProjectConstants.lua). Engine-defined Classic constants are matched by their provided names, not synthesized numeric comparisons or a catch-all non-Retail branch.

The pinned client-authored source is retrieved through the Gethe mirror, which is not a Blizzard-owned SDK publisher. The ledger now records each source `version.txt` and hashes for the exact files inspected. Existing `apiDocuments` entries describe declaration presence; a missing file hash is not proof of a missing API. Shared ProjectConstants files do not enumerate every engine-provided product constant.

The source snapshots identify Retail 12.1.5.70448, Era 1.15.9.70003, progression 5.5.4.70469, Anniversary 2.5.6.70006 and Forever 1.60.1.70450. The refreshed [progression snapshot](https://github.com/Gethe/wow-ui-source/blob/15c8a754451ce09a688be11ffa03c064e4973c14/version.txt) replaces the earlier source revision; the five hashed spell, spellbook, aura, assisted-combat and event-validity declaration files are byte-identical between those revisions. This scoped comparison does not establish equivalence of the entire API or native accessibility.

Separately captured Blizzard [Retail](https://us.version.battle.net/wow/versions), [progression](https://us.version.battle.net/wow_classic/versions) and [Era](https://us.version.battle.net/wow_classic_era/versions) product feeds report version/build metadata, with response hashes retained in the ledger. Those feeds do not supply an addon Interface number. Neither a mirror version nor a product build authorizes calculating a new TOC Interface value. The user's Anniversary 2.5.6 / 20506 observation is separate native evidence; it is not equated with the mirror's build number.

Local release checks exercised the declared historical 11403, 30400 and 90207 packaging routes. They verified archive payload, vendor bytes and load order, with the selected Interface line differing by route. They do not establish current Era, progression or Retail loading, API readability, taint safety or gameplay acceptance. The source TOC additionally lists Forever Interface 16001, based on the installed client's lastAddonVersion and independently matching installed Forever addon metadata. This does not certify Forever APIs or gameplay, alter its restricted combat-data policy, or add a release/publishing route.

The new Platform boundary records API declaration presence separately from readability. Native-assisted availability is probed independently; a declared function is not proof that the feature works for a character. `runtimeVerified=false` is deliberate until actual smoke evidence exists. The metadata boundary does not yet migrate every historical API call or select recommendation engines; old callers remain tracked modernization work.

Cold item-cache warmup now uses the existing protected item-display adapter instead of directly requiring the legacy `GetItemInfo` global. Offline startup checks cover a modern `C_Item`-only surface, legacy fallback when the modern method is absent, and unavailable, restricted or failing metadata without blocking initialization. This advisory warmup does not alter combat-data policy. The installed Forever client's legacy alias availability, full OnEnable lifecycle, native event registration and gameplay remain unverified.

Mode facts are raw: a season ID, hardcore flag, game-mode record and self-found-allowed flag describe different things. Self-found allowed must not become a claim that a character actively uses it. Missing metadata remains absent. Unknown projects keep an explicit unsupported policy rather than borrowing another family's rules.

Current automated guards check Lua/load graph/vendor files, literal English keys and registered help/category metadata. They are not proof of optimal rotations, completed translations, client taint safety, or live API accessibility. Error-report redaction is best effort, with explicit original-text preview/copy; anonymized analytics/LLM exports remain deferred.

Development installation: the source directory is symlinked directly into the user's WoW AddOns directory. Edit the source and use `/reload`; no ZIP/deployment step is needed. Do not generate further deployment archives unless requested.

Item action readiness uses a normalized cooldown record from `Platform:GetItemCooldown`. It prefers `C_Item`, then the older container namespace, then the legacy global, and accepts validated boolean or `0/1` enabled flags. A failed or restricted observation does not trigger fallback to another backend. The generated Blizzard [Item API](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_APIDocumentationGenerated/ItemDocumentation.lua) and [Container API](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_APIDocumentationGenerated/ContainerDocumentation.lua), inspected on 2026-10-18, expose these different flag forms. Missing metadata remains unavailable; this does not certify native API access in a live client. Legacy UI item-set helper callers still need migration.

The five item predicates now use protected per-evaluation observations through `Core/item_conditions.lua`. Have Item In Bags uses a separate bag-only snapshot, including a declared reagent bag, rather than treating the general ownership count as a bag count. Multiple stacks of the first carried candidate are combined; different candidate items are not summed. The other predicates select the first carried or equipped candidate. Missing item sets, unresolved names, incomplete metadata and restricted results remain unavailable under NOT. An explicit empty item list is known absence. Native metadata supplies item descriptions when available.

Item Available retains its level/cooldown policy and uses the same Classic/later global-cooldown probe as spells. Actual item actions still enforce their own ownership, usability and range. Item Cooldown measures nonnegative remaining seconds at the evaluation timestamp; a disabled timer is unavailable, not an invented zero. Legacy UI item-set helpers and other remaining raw callers still need migration; these five predicates no longer depend on those helpers.

Raid marks (`docs/raid-marks.md`) have fake-client coverage. Direct `SetRaidTarget` worked in TBC; Retail rejected the
call as protected and returned a secret marker in the user's test. Mark features are disabled on Retail and Forever.
Other marker behavior and `UnitTokenFromGUID` availability need real-client checks. `/rm debug marks` reports capabilities.

## Client API manifests and loadDeprecationFallbacks

`tests/fixtures/client_api_<client>.lua` (retail 12.1.5, forever 1.60.1, mists 5.5.4, tbc 2.5.6, era 1.15.9) classify every client global and C_* function the addon references, plus every name a `Blizzard_Deprecated*` fallback defines: native, provided only while the `loadDeprecationFallbacks` CVar is on (with the C_* API it wraps), removed, or never present. `tools/generate_client_api.py` builds them from a Gethe/wow-ui-source checkout (Blizzard's UI code, its deprecation addons and their TOC load conditions) and Ketho/BlizzardInterfaceResources (in-game dumps of every global function taken with the CVar off, plus enums, global strings, frames and CVar defaults); the revisions are recorded in each manifest. Fixtures built by `tests/fixtures/addon.lua` and `tests/fixtures/client_baseline.lua` install them (`tests/fixtures/client_api.lua`): a name the client does not provide is nil and a later stub of it is dropped. Retail and Forever fixtures model the CVar off, the Classic families their default (on); `F.new(..., {fallbacks=...})` selects either. `tests/client_api_surface.lua` fails when addon code reads a name some client lacks without its native successor in the same file, or outside the reviewed feature-detected reads it lists.

`loadDeprecationFallbacks` defaults to `1` on all five clients (Ketho's CVar dumps). A name that is fallback-only therefore works for most players; the addon still must not rely on it, because a player can turn the CVar off and Blizzard says the fallbacks go at the next expansion. Since 2025 the Classic clients moved much of their API behind it too: the action-bar queries (`HasAction`, `IsUsableAction`, `GetActionCooldown`, `IsActionInRange`, vehicle/override/possess bars), `CombatLogGetCurrentEventInfo`, `UnitAura`, the `GetItemInfo` family, `GetTalentInfo`/`GetTalentTabInfo`/`GetActiveTalentGroup`, `IsSpellKnown`, `SendChatMessage` and `DoEmote`; Mists removed the `GetSpecialization` globals outright. The 12.x change to read the action bars through `C_ActionBar` (71742b4) is therefore defensive for clients with the CVar off: with the default CVar the globals exist, and the Retail no-glow it was written for came from the removed `BOOKTYPE_SPELL`/`BOOKTYPE_PET` (3b23836).

With the CVar off on Era, the vendored ThreatClassic-1.0 (an AceAddon that enables itself; Rotation Master does not register or use it there, because Era has a native `UnitThreatSituation`) captures a nil `CombatLogGetCurrentEventInfo` and `UnitAura` and raises a Lua error on combat-log events. It is left alone because other addons may share its LibStub instance. LibClassicDurations is registered by Rotation Master, so it is registered (and read for aura durations) only while the globals it captured exist.
