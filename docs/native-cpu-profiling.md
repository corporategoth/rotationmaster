# Native CPU captures

General → Debugging has **Capture CPU (10s)**, **CPU report**, and **Cancel capture**. These diagnostic actions use current runtime settings and do not apply a settings draft.

WoW's `scriptProfile` must already be enabled before a reload. If capture reports that it is disabled, enable it with `/console scriptProfile 1` and `/reload`. RM never changes that setting or resets shared CPU counters. Profiling adds overhead to the client; disable it with `/console scriptProfile 0` and `/reload` when the investigation is finished.

For a normal gameplay measurement, close configuration and run `/rm cpu start`. Leave the same rotation, polling interval, and character activity in place for the ten-second capture. Then use `/rm cpu report` to open the selectable, copyable report. `/rm cpu cancel` cancels an active capture. The buttons provide the same actions without chat commands.

Compare separate captures with the rotation active and inactive. Record whether the character was idle or fighting, which visual effects and preview were enabled, and the polling interval. The report records configuration visibility and combat state at its boundaries; it cannot prove those states stayed unchanged between them.

The report uses differences between native cumulative counters for the same function objects. Exclusive costs rank the selected functions; inclusive costs include their callees and overlap, so they must not be added together. Call counts and per-call costs help distinguish frequent inexpensive work from a few costly calls. A separate Structural validation calls line always reports ValidateEnvelope and ValidateBody counts, including zero; missing, replaced or failed counters say unavailable. Shared function objects overlap and must not be summed. This distinguishes full structural checks from dependency-freshness scans even when validation falls below the top timing rows. This is selected coverage, not a complete accounting of every function, frame script, native operation, or shared-library cost. Collection overhead is part of the measurement.

An additional **Inclusive scopes** section ranks up to ten of the same selected functions by inclusive cost. It can reveal an expensive parent whose own exclusive work is small. It reuses the collected snapshots; repeated and overlapping rows must not be added together. The extra section can be shortened or omitted when the report is large; existing report lines are retained.

Missing APIs, invalid counters, counter resets, and functions replaced during capture are reported as unavailable. A capture must not turn those cases into zero CPU usage. Captures remain in session memory and include no source code, condition values, or character ownership keys.

## Cache and validation boundaries

The exact-key observation cache reuses complete return tuples, including false and nil results, for the same function object, receiver and argument tuple. Normal condition evaluation currently creates a cache for each root condition tree. Environment updates have a separate cache, and different normalized adapters also have distinct keys. Thus a cache hit within a tree does not mean the underlying WoW API runs only once per polling tick.

Sharing every cache across a tick changes observable behavior when custom callbacks change state before a later card. Performance changes must preserve that behavior or introduce explicit safe invalidation boundaries. Native observations, optional provider responses and ownership checks have different freshness contracts.

Runtime assets already retain validation results while their record and dependency stamps remain current. Repeated stamp checks still inspect dependency identities to catch direct table changes and changes made by callbacks before advice is published. Optimizing these checks must retain retirement on dependency, record, profile and context changes. Host timing probes and dispatch-count regressions help identify improvements; a comparable native capture is still needed to establish a gameplay CPU reduction.

Private eligibility projections now omit unused client metadata on the originally owned path. Public GetClientInfo and GetRotationContext retain their complete bodies and shapes; overridden methods and missing private readers retain full public dispatch. Class, level, build, vehicle and pet-battle facts remain fresh at every existing check. The private projection performs the work previously attributed to some public GetRotationContext calls, so fewer calls in that selected profiler row do not mean fewer authority checks. Compare total addon CPU alongside selected rows.

A controlled actual Shaman starter probe reduced locale queries from 18 to 5 per idle no-target poll, and from 15 to 3 with a target. Other instrumented native queries and the selected spell stayed the same. These are offline query-count results, not a measurement of native CPU savings or the user's exact saved clone.

Portable-data validation keeps its complete traversal, deterministic key order and all resource limits. Successful checks now track path keys privately instead of constructing diagnostic strings for every value. On failure the same diagnostic path is rendered, with the same key truncation and parent/child locations. This reduces formatting work without caching validation by object identity.

An immediately adjacent owned library-generation check can reuse its completed dependency scan for the following stamp comparison. Reuse requires a private definition-owned method proof, an unchanged path that did not call initialization, raw-present field paths and callback-free comparison operands. Changed primitives, overrides, inherited lookups, metatables on dependency maps or retained stamp/generation tables, and missing proof keep the second public scan. AceAddon and AceDB object metatables are permitted only because all accessed slots are proven raw-present; the code neither compares nor stringifies those objects. Primitive checks require native functions stored directly in the original Lua environment; every inherited or missing lookup retains the original scans and getter order. Protected metatable descriptions cannot authorize reuse. Missing Lua environment inspection or changed helper environments also disable reuse. Every later independent boundary still scans again. The trusted addon loader/private handoff assumes standard primitives at load; it does not authenticate a hostile replacement of the complete loader itself.

The report also always shows the execution-index call count, including zero, even when indexing is below the top timing cutoff. It uses the same existing native snapshot and pointer-deduplicated row; it adds no function wrappers or idle sampling. Unavailable or replaced counters stay unavailable. A lower call count establishes less rebuilding, not the CPU cost of private reuse checks; compare total addon CPU as well.

The main runtime can reuse one private successful execution index while its complete input graph remains unchanged. Every reuse still compares all raw keys, values, table identities and metatables; edits to unused fields, cooldowns or branch arms also invalidate it. Failed checks, overrides, changed source environments or uncertain ownership take the original fresh path. Public indexing and sequence calls remain fresh. The shared executor receives new row/path metadata each invocation, so callbacks cannot alter a retained index through a path helper. Live condition and action observations continue at the configured polling interval. This cache assumes standard primitives at trusted source load and excludes privileged mutation of its private proof machinery.

The copyable CPU report includes **Execution index proof start/end** snapshots. These fixed, source-free reason codes come from the original private owners of the runtime, sequence executor, portable reader and index reader. They are collected only at capture boundaries; opening the report adds no probes, and idle gameplay adds none. An unavailable probe is explicit. Boundary readiness does not prove every poll used the private path; compare the execution-index call count and the inclusive scopes as well.

The proof records the captured/current string lookup shape (`table`, `function`, `other`, or `unavailable`). A different global `string` table is advisory (`string-global=0`), since method syntax uses the actual native string metatable. Reuse requires the captured native lookup table and its original `match`/`sub` methods to remain unchanged. A function-valued lookup or uncertain ownership retains fresh public dispatch. These checks are included in **General → Debugging → CPU report** and `/rm cpu report`; no copy from chat or separate `/run` command is needed.

## Observation-cache comparison

General → Debugging → **Bypass observation cache (reload required)** saves a diagnostic request immediately, independently of the settings Apply/Discard controls. Reload after changing it in either direction. The displayed active mode stays fixed until reload; changing a request during capture cannot switch its dispatch. The request is account-wide within RM's global data, independent of the selected settings profile.

The mode is selected once immediately after AceDB initialization, after SavedVariables are available. Existing helper references captured while addon files loaded follow that selection without changing their identities. With the box clear, RM uses the original cache helpers without an added per-call mode check. With it checked after reload, the standard `getCached` and `getRetryCached` entry points use their original nil-cache path. This preserves function-name lookup, argument/receiver tuples, return counts (including nils) and thrown errors, while skipping cache lookup, storage and argument-key construction. Each invocation reads again rather than reusing an earlier observation. Direct mode adds one delegating Lua call to reach the unchanged original implementation; its measurements include that diagnostic overhead. Custom code containing a separate copied cache implementation retains that implementation. Execution-index reuse and validation are unaffected.

For a paired measurement, capture the same rotation, activity, polling interval and UI state in cached mode, reload into direct mode, then repeat. Each copyable report's start/end lines identify `observation-cache`, `requested` and `reload`. Compare total addon CPU and API/helper call counts; inclusive rows overlap. Direct mode can remove table work and increase underlying reads, so the native captures determine which cost dominates. Reloading between modes also starts with fresh cache state; the diagnostic does not enumerate or clear caller-owned tables.

## Fixed cache-helper counters

The CPU report also samples the original `getCachedInternal` and `packResults` function objects through their existing source-owned getter. A separate two-row appendix reports their exclusive/inclusive deltas and calls, including zero or unavailable results. The original ranked coverage and its counts remain separate. Shared pointers reuse snapshots; at most eight extra native counter queries run across a complete capture, with no extra gameplay polling or report-read queries.

These counters include every caller sharing those original objects. Archived helper copies can still call them while standard helpers use direct mode, so a direct capture does not guarantee zero `packResults` calls. Independently compiled helper objects remain outside this fixed selection. Inclusive times overlap; the public wrapper counters alone do not explain private costs or establish a tail-call accounting rule. Missing or changed source ownership stays unavailable. The appendix is omitted when it cannot fit without growing an already oversized report.

When the captured native string-method lookup is unavailable as a table, the private execution-index reader cannot ever satisfy its existing ownership proof. That case now binds a reader which declines immediately and performs the same retirement; fresh public indexing remains in use. The supported reader and all positive eligibility guards stay unchanged. This removes repeated unsuccessful proof work under the existing trusted, pure source-owned loader contract; arbitrary substituted private installers with callback side effects are outside that contract. Host timings do not establish a native CPU improvement, and the report can correctly keep showing fresh indexing and the same unsupported proof reason.

## Retained catalogs and animation activity

An additional capture-only appendix reports start/end key counts for the private spell-ID/name maps and item current/index/blocked maps. Exact uncapped counts show signed net growth; capped counts are lower bounds and cannot establish an exact difference. These are record counts, not allocated bytes or proof of a memory leak. A temporary observer counts successful global spell/item metadata arrivals during capture; another addon can initiate those loads. Counts retain no IDs or names.

The appendix also inspects a bounded set of RM's known button slots. It reports visible overlays and associated shared-glow frames separately from RM sequence-timer handles. A handle does not establish that a timer is executing. Shared glow association does not establish exclusive RM ownership. Fixed animation-function views can measure the original RM overlay callback and shared Pixel, Autocast and Blizzard glow callbacks when a starting function is available. Shared counters include all callers, and Proc uses native animations. End-only callbacks lack a starting baseline. Missing or changed owners and ambiguous callbacks remain unavailable.

Collection runs only at capture boundaries and during the temporary metadata observation window. It adds no normal gameplay polling, all-ID scan, frame enumeration, forced garbage collection or persistent diagnostic data. Report reads perform no new collection. The observer retires on completion, cancellation, timer failure or addon disable. New function pointers share the existing bounded native-snapshot pool; old ranked rows and private-cache measurements remain separate and overlapping inclusive costs must not be added. The appendix is omitted when it cannot fit inside the existing report bound.

For memory investigation, compare ordinary captures before considering a catalog-retention policy change. A rise in counts can identify a retained data path but does not measure the post-collection heap. WoW Task Manager's memory growth/min is a session-average calculation, so one-off initialization growth can remain visible after current allocation activity has subsided.
