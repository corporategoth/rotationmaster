# Explicit memory lifetime capture

`/rm cpu memory` starts a ten-minute diagnostic. General → Debugging provides the same Capture memory action, Stop memory capture, and a copyable Memory report. `/rm cpu memorystop` ends it early; `/rm cpu memoryreport` reads the last result. The command does not apply a settings draft or change polling.

The module reads `collectgarbage("count")` at most 601 times, using a one-second timer, and retains aggregate start/end/min/max plus observed decreases of at least 256 KiB. It stores at most 21 detailed rows at actual observed thirty-second boundaries, reserving one row for completion even if the periodic cadence drifts. A late timer creates an actual late sample rather than replaying missed seconds. Stop/timeout retires the capture before cancelling its own two timer handles; old or reentrant callbacks cannot replace a newer capture. No work starts on load, or when a completed report is viewed.

Only capture start and completion explicitly refresh addon attribution using the available `C_AddOns` or global `UpdateAddOnMemoryUsage` API, then query `GetAddOnMemoryUsage` with the actual loaded addon name: at most two expensive scans per completed capture. Intermediate detailed rows read the cached attribution without refreshing and label its age unknown; another addon may have refreshed it, so the sampler does not infer freshness. Cancellation does not add a scan. A late or repeated timeout cannot repeat the final scan. Start/end attribution remains in the report summary even if detailed rows exceed the text limit. Refresh and sampler-body durations are reported separately, unadjusted, using the optional profiling clock. The whole-heap value precedes that refresh. If attribution is missing, fails, or is restricted, the value stays unavailable while whole-heap sampling can continue. Refreshing addon attribution can cause a hitch; this is opt-in diagnostic overhead, not ordinary RM CPU. No WTM integration or WTM dependency is required.

Whole-Lua heap is shared across addons. Reported addon attribution is not an inventory of retained objects and does not establish exclusive ownership of shared libraries/objects. A downward heap step is an observation consistent with collection, not a native GC statistic. The diagnostic never invokes collection, GC control, reset-CPU APIs, native MeasureCall, or evaluator hooks. CPU/runtime capture flags describe detailed-row boundaries only; concurrent instrumentation can affect observed memory.

The existing CPU activity readers provide capped source-owned cardinalities for spell/item catalogs and active RM visual associations. The scalar export omits private maps, native frames, callback functions, IDs and names; native accessor initialization happens only on explicit diagnostic use. Retained catalog counts cap at 4096 keys. Visual traversal keeps its existing 128-button/512-slot bounds. A sequence count means timer handles, not measured executions.

The memory module also counts known public unit/history/cache roots. It traverses only the documented fixed history levels, with a shared 8192-node budget and 4096 count limits. It does not recurse through arbitrary values, SavedVariables, debug upvalues or the global Lua heap. Incomplete counts are lower bounds marked `>=`; unknown counts remain unavailable. No keys, recipient/unit names, GUIDs, source strings or error payloads enter the report. `Diagnostics:GetReports()` is deliberately not used because it deep-copies full error records.

A stable trough with rising/falling memory and flat retained cardinalities can suggest disposable allocation, but does not identify the allocating function or prove a leak. Growth in particular cardinalities identifies a container class for subsequent source investigation, not its exact retained bytes. Existing native runtime allocation/deallocation reports measure gross activity during calls, not retained heap; subtracting their totals is not a retention measurement.

If installed WTM exposes its existing public `WoWTaskManager.Processes.byName[addonName].spikes` and `lastSpikeAt` scalars, each valid heap tick also observes them without calling WTM methods or updating its memory/CPU state. The report counts increases that co-occur with an observed whole-heap decrease over the same actual sampling interval, and includes counters in detailed rows. Counter resets, object replacement and missing observations establish a new comparison baseline. Missing WTM simply reports this optional correlation unavailable. Interval timing is coarse and may stretch after a delayed callback; a count increase need not identify a single frame or a single collection. The last-spike offset is shown only for timestamps within the capture.

WTM's Spikes display concerns slow frame-time incidents, with sampled addon CPU-window correlation. It is not a count of proven RM-caused hitches or network-latency incidents. This memory diagnostic does not promise to resolve those spikes. Live WoW acceptance remains unverified until an explicit native capture is completed.


## Explicit command durations and completion

`/rm perf memory` defaults to 600 seconds; `/rm perf memory N` accepts 1–1800 seconds. Sampling remains once per second and detailed counts once per thirty seconds. Per-run caps are `ceil(N)+1` heap samples and `ceil(N/30)+1` detailed rows; report text retains its existing byte bound. Attribution refreshes remain start/end only, at most two attempts per run.

`/rm perf memory stop` calls `CompleteMemoryCapture`: sample the final boundary once, retire both timers, and retain a stopped report. A stop reentered from an active sampler callback retires without recursively sampling or overwriting newer captures. `/rm perf memory report` opens the copyable result. The existing `StopMemoryCapture` cancellation path used by legacy controls and addon disable remains unchanged and does not request an extra attribution refresh.
