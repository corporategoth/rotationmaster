# Shared condition and utility authoring

Built In source browsing, the compiled utility registry, the Functions roster, dependency bundle review and optional embedded LuaWorkbench editing are implemented. Native WoW verification of the new controls remains necessary; offline fixtures cover data, ownership and execution boundaries.

Built In and custom conditions share one definition contract: identifier, display name, description/help, icon, field schema and the existing callback arguments. Both run compiled Lua functions. Custom source is compiled on registration/save, rather than interpreted for every recommendation. Runtime source kind must not alter condition semantics or platform restrictions.

Named utility functions use the same source ownership model. Their records contain an identifier, display name, description, argument names/documentation, Lua body, dependency references and optional return-value documentation/schema. The function body returns values with ordinary Lua `return`; the editor need not require a separate return expression. Cache, evaluation context and platform adapters remain explicit inputs to helpers that need them.

A shared browser exposes both Built In and custom conditions, and a utility browser exposes both Built In and custom utilities. Each shows source, arguments, help and dependencies in the same editor. Packaged entries are read-only; either kind can be duplicated into an editable custom record with a new identity. A duplicate retains its origin ID/source version for later comparison. Imported source stays data until explicitly applied through the existing trusted-code review path.

Keep one authored source of truth. Lua files can remain the source format; a build step can extract/generate the browsable source catalog, source maps and hashes. CI must reject a stale catalog. Do not hand-maintain a second copy or attempt to reconstruct text with bytecode dumps. Built In callbacks currently close over local functions/constants; migrate those dependencies into declared utilities or documented system bindings before promising an independently editable copy. Framework lifecycle and arbitrary Blizzard globals are not automatically user-authored utility definitions.

Runtime registration validates identifiers, argument schemas and dependency availability, rejects utility cycles, compiles once, and installs changes atomically. Cloning a condition should retain explicit helper references by default; offer a dependency-copy plan for making an independent set. Built In utility source is visible and duplicatable under the same rules. Never silently shadow a packaged helper with a custom function of the same ID. Imports/exports carry dependency IDs and versions, and comparison shows helper-source changes as well as condition changes.

Implementation sequence: formalize the shared source record and utility contract; build one single-source representative condition/helper migration with dependency tests; add readonly source/duplicate views; migrate the remaining built-ins and add corpus checks. Existing rotations and custom definitions need a backward-compatible adapter throughout.

## Dependency-aware transfer

Export a condition or utility together with the transitive closure of its custom utility dependencies by default. Provide an explicit Include custom dependencies checkbox; turning it off still exports a requirements manifest (IDs, names, compatible versions/source hashes). Packaged utilities are referenced by ID/version instead of duplicating their code. A clone of a packaged utility is custom and belongs in the closure. Resolve dependencies from declarations and source analysis without running exported code. Detect cycles, repeated IDs, excess depth/count/source size and unresolved references before producing a bundle.

Import preview lists the root definition and every included dependency: original name/source, existing match, proposed destination name and chosen action. Identical versions can reuse the existing utility. For a conflict, offer reuse existing, replace editable existing, or import a renamed copy; Built In entries cannot be overwritten. Show effects on existing consumers before replacing a custom utility. Preserve all original names/provenance separately from destination names. Excluded dependencies have no overwrite/rename rows, but missing or incompatible requirements must still be reported.

Build a complete identity/reference remap before commit. References between the condition and utilities, and between utilities, must all point to the selected destination identities. Prefer stable IDs plus explicit named bindings so ordinary renames change data references rather than arbitrary source strings. If editable Lua identifiers must change, use scope-aware Lua token/AST rewriting; never replace substrings in comments, strings, unrelated locals or API names. Preview the resulting source diff. Dynamic undeclared references require a diagnostic or explicit binding rather than guessing a dependency by executing code.

Stage the whole plan; validate schemas, source syntax, dependencies and target versions; re-check the destination identities at Apply, then install atomically with rollback on registration failure. No partial utility replacement should survive a failed root-condition import. Imported Lua remains subject to the explicit trusted-code review/apply boundary. Existing single-entry import dialogs can share the transfer shell while bundle conflicts use a dependency table and a source/diff pane. Root Replace/Create alone is insufficient for a bundle.

## Availability and disabling

Built In/custom source browsers and editors must visibly flag incomplete, invalid or unavailable definitions with a reason. This applies equally to utility functions. Syntax/schema errors, missing arguments/bindings and disabled/unresolved dependencies affect the whole dependency graph; a definition can remain visible for repair while being unavailable for execution. Condition and function editors flag source/schema errors and graph availability. Runtime graph validation and source-browser warnings share the registry.

Custom conditions and utilities each have a definition-level Enabled/Disabled control. Disabling preserves source, metadata and references. It is distinct from hiding a picker entry or disabling a node occurrence in a rotation. All direct and transitive consumers become unavailable/inoperative, rather than false. Negation and False branch arms must not convert unavailable data into permission to advise an action. Re-enabling restores usability only after syntax/schema/dependencies validate. Changes must invalidate recommendation caches and refresh editor/browser availability immediately. Export/import retains enabled state, with clear review when a dependency is disabled; import choices cannot silently enable an existing disabled utility.

Current definition availability implementation: custom-condition source accepts an optional `disabled` boolean that travels in condition transfers. The condition list and source editor stage an Enabled/Disabled pill through Apply/Cancel. Disabled sources register inert metadata, skip registration hooks, and are rejected by runtime evaluation and rotation dependency validation. Disabling can preserve syntax-broken source for repair; re-enabling must validate it. Registry revisions refresh packaged/default validation. Registration failures restore the former runtime definition and saved source. The utility registry propagates unavailable status through explicit bindings. Cleanup runs while the former graph is still usable, and suspended condition consumers resume only after successful registration against the recovered graph.

## Current custom-condition editor

Selecting or adding a custom condition opens its source editor in the Conditions page's right pane. The whole definition, all callback buffers, and its picker/category preferences form one staged edit. Apply validates and installs the source before saving preferences; leaving with changes offers Apply, Discard or Cancel. Built In conditions now use this same pane with immutable source, metadata and schema. Hidden/Switch/category preferences remain editable. Duplicate creates a custom source draft, preserving explicit packaged helper bindings and the original parameter aliases. The displayed signature always shows the complete public callback arguments; compatibility aliases inside the generated wrapper preserve older bodies. Graph-only AND/OR/NOT remain structural controls rather than invented source callbacks. The Functions page uses the same code provider, typed metadata, readonly Built In source, Duplicate, Compare, staged Apply/Discard and dependency-aware transfers.

Each callback shows its description, typed argument and return documentation, then Undo / Redo / Reset, then the function signature immediately above the code area. Callback edits survive switching callback tabs or changing metadata. Reset is undoable and restores the last saved callback, or the template for a new condition. The whole-definition Apply saves all callback buffers. Known generated template header comments move into the documentation; authored comments are preserved.

The native editor supplies a visible input border and delegates left-click caret placement and keyboard navigation to the EditBox. Escape and right-click while editing route through the owner's pending-change prompt. The native caret repair was confirmed in game. Offline fixtures verify those handlers and draft transitions; the newly embedded advanced provider still needs native input and layout verification.


## Generated packaged source and utility lifecycle

`tools/generate_builtin_sources.py --write` collects callback source positions and captured helpers offline across the reviewed client inventory, then extracts source bodies from authored condition modules. The generated catalog and managed local-getter suffixes are checked by `tools/check`. The game never reads source files, inspects bytecode or uses debug upvalues. Packaged conditions still execute their original closures. Clones compile once and resolve declared stable binding IDs, preserving class-specific values and shared optional-integration state.

`Core/functions.lua` stores typed argument/return metadata and explicit alias-to-ID dependencies. Registration compiles source; calls reuse compiled functions. Invalid, disabled, cyclic or missing dependencies make transitive consumers unavailable, including beneath NOT. Saved consumers remain registered as unavailable metadata so enabling a dependency can restore them. Before changing a graph to unavailable, cleanup hooks run against the old usable graph; suspended consumers resume registration after recovery. Trusted hooks can have external effects; syntax checking is not sandboxing.

## Optional advanced editing

The optional provider embeds LuaWorkbench's advanced editing, completion, knowledge, navigation and debugging inside RM's themed panes, with independent draft ownership. It works from released source without requiring upstream modifications. The installed release exports its Workspace but not the private Query.Editor table; autocomplete and debug ownership checks assume their namespace's Console.input. The adapter supplies an isolated compatible namespace and reuses pinned upstream MIT components where private references prevent direct attachment. It does not replace the user's Workspace, snippets or saved state. An upstream clean embedding API is optional follow-up, never a prerequisite. Native RM editing remains supported with RM argument/function documentation and completion; no separately maintained WoW API knowledge base.


The vendored factories are generated by `tools/sync_luaworkbench.py` from the pinned commit recorded in `Libs/LuaWorkbench-Embed/manifest.json`. Upstream file hashes, generated-file hash and MIT license are retained; `Libs/UPSTREAM.json` protects the generated files. Embedded instances suppress upstream slash registrations and automatic event automation. The installed addon is detected as the user's opt-in capability provider, but its private tables, snippets, drafts and saved variables are never borrowed. The Integration preference can select native/plain editing instead.

Debug is an explicit action on the current buffer with a separate test-argument expression. It does not register or replace a saved utility or live condition. Debugged Lua and argument expressions are trusted code with addon access. Closing a provider stops its debugger and disposes its own input, popups and event subscriptions. Syntax checking only compiles; it does not run the buffer.

Native/plain editing reuses the same released completion parser against RM-only documentation. Callback parameters, schema fields, explicitly bound helpers, `addon`, `L`, and curated public RM helpers feed the shared symbol model. Hover/signatures show typed documentation; Ctrl-click a bound/public helper navigates to its source after pending-edit confirmation. WoW API documentation and completion come from LuaWorkbench's APIHelp/KnowledgeBase components and Blizzard documentation; RM does not maintain another WoW API database. Contextual spell/item/unit insertion into code is not implemented.

## Public helper reference and field rendering

`tools/public_helpers.lua` contains typed documentation and call names for the curated public authoring API, never copied function bodies. The generator extracts the actual implementation from its authored module alongside captured condition helpers. The Functions roster exposes those Built In sources and allows editable duplicates. Public colon-call completion hides the implicit `self` argument; a local binding to that same function retains the explicit argument. Early-loaded modules queue their live getters until the catalog registers.

New Fields UI templates receive `addon`, `L`, `parent`, `spec` and `value`; they do not create an AceGUI local. The native `CreateConditionEditBox`, `CreateConditionSlider`, `CreateConditionDropdown` and `CreateConditionCheckBox` factories implement the existing widget contract and can be added to the callback parent. Legacy widget callbacks still receive a compatible container and remain supported. Removing this compatibility bridge is separate from replacing native field controls.

Readonly source display strips only indentation shared by every nonblank line. Packaged executable source, exports and comparisons retain the original bytes. Editable source preparation removes leading blank lines and uses the bundled Lua formatter before capturing its initial baseline; multiline literals keep their values. Reused source forms reset their field baselines between definitions. New clones require Apply to create them without marking untouched fields as edited. Readonly inputs are disabled at the native input boundary rather than accepting and reverting typed characters. Field schema presentation uses a stable label, whole-viewport change marker, and a multiline Advanced editor; graphical schema actions stay outside its scroll region.


## Unified condition Test and debugging

The condition-level Test action sits immediately left of View Changes, independent of the selected code tab. Built In and custom conditions use the same dialog. It renders Fields UI and Help together against detached values; opening it does not validate or evaluate default values. Committing a field value schedules a single validation/evaluation refresh, while Run test explicitly uses the current values. Invalid values skip evaluation; results distinguish True, False and Unavailable. Closing commits pending valid input without evaluating during close.

Live checking is opt-in and throttled to one attempt per half-second while visible. Hide, close or invalidated source ownership stops it; source/registry changes invalidate compiled callbacks and old results. Bounded plain samples are saved separately in `db.global.condition_test_values`; a session's configured state records owner, key, profile, global store, schema and binding identity. Merely displaying persisted/default values does not configure them for debugging. A user input commit or explicit Run configures detached samples, which are returned as copies. Widget generations protect released callbacks, and errors go through RM Diagnostics with source redacted.

LuaWorkbench condition debugging receives arguments from Test instead of an editable raw argument expression. Evaluate, Validate and Summary require configured values; Evaluate receives a fresh cache and current evaluation timestamp. Lifecycle callbacks receive the condition tag. Fields UI and Help receive separate disposable render surfaces while the source pane stays visible. Stopping debug or closing its surface releases all tracked controls and callbacks. Temporary allocation wrappers exist only during synchronous coroutine resume and are restored before yielding to the game. Generic utility functions retain explicit test-argument expressions.

The embedded Output action opens the shared themed text shell with scrolling, Copy, Clear and Refresh. Full error messages are captured before upstream status formatting truncates them. Context and retained console output are included; closing the provider closes its report. Debug execution remains an explicit trusted-code action and never replaces a live saved definition.

Function and condition bodies are syntax-checked as independent chunks before insertion into generated wrappers. This rejects an unmatched `end` that could otherwise escape into wrapper-level expressions. Compiling a registry or import preview never executes supplied bodies. Dependency import apply also treats failed resumed-consumer registration as a transaction failure: attempted resources are cleaned using staged helpers, and the former saved/runtime graph and consumer flags are restored. Trusted external side effects remain best-effort to reverse.


## Function metadata and documentation hover

Built In and custom function sources use the same metadata controls. Built In inputs and code remain read-only; selected editor providers still supply API knowledge. Providers without a working read-only control fall back to the native locked editor. Type dropdowns include primitive and registered documented types, retaining imported unions; Nullable adds or removes only `nil`. Multiple return rows describe Lua's ordered return values. Descriptions wrap from their beginning, and the source corner control expands the code area while retaining the metadata draft and provider.

The Name field is a valid Lua identifier forming the last component of its namespace-qualified call. It is separate from the stable registry identity used by dependencies and imports. Legacy display names are normalized for editing before the draft baseline is captured; saved records and references remain untouched until Apply. Binding rows show the name in code (qualified path or legacy alias) and a source helper with its module or custom identity, distinguishing captured helpers such as AceGUI. Renaming a binding never rewrites source text. Binding changes retain saved-baseline markers.

Hover uses the same token spans as the embedded editor, covering identifier glyphs without parentheses or adjacent arguments. Native measurement text uses the input's left/top alignment. The pinned LuaWorkbench adapter accounts for line spacing exactly once when normalizing glyph rectangles. Bare documented function references (for example UnitExists passed to getCached) use LuaWorkbench APIHelp rather than a separate RM API database.


Entity deletion is immediate after confirmation. Outstanding edits use the normal Apply/Discard/Cancel navigation prompt first. The delete operation then resolves the current saved entity, commits its removal and runtime cleanup, and opens a clean successor; deleting the last entry leaves a clean empty page. Deletion does not create a separate draft state or activate Apply/View Changes on the next entity.


## Utility namespaces and editor consistency

Built In functions derive namespaces from their source path: `utils.lua` becomes `utils`, and `Platform/spells.lua` becomes `Platform.spells`. Custom functions have editable Namespace metadata (new functions default to `custom`; legacy sources without it retain `functions`). The roster filters inferred namespaces alongside Built In/Custom and search; namespaces have no separate maintenance entity. Names and namespaces are staged until Apply.

The canonical invocation is `namespace.name(...)`. A Lua colon call is syntactic receiver passing (`object:method(x)` equals `object.method(object,x)`), not a namespace declaration. Namespaced bindings use dot calls; methods include their original receiver explicitly. The source signature shows the qualified call without an Invoke label or a separate Existing API line. Original addon dot/colon APIs remain available for saved definitions. Invocation guidance belongs in Help.

A binding maps a qualified call path to a stable registry ID. Compilation creates callback-private nested tables rather than addon globals. Accepting completion stages code and dependency as one undoable transaction, rolling both back on failed or stale insertion. Existing simple aliases and `functions.alias` remain supported. Renaming source metadata never rewrites existing consumer code or binding paths; bundle imports remap dependency IDs without altering call paths. Conflicting prefixes, reserved/library roots and parameter shadows are rejected.

RM symbols include typed public addon values and callable helpers with their actual receiver and origin. Client WoW API metadata continues to come from LuaWorkbench. An undocumented global callable is identified honestly without inventing a signature or Blizzard attribution for RM helpers.

Run executes the prepared callback without debugger instrumentation; Debug starts the debugger. Condition data-dependent callbacks use configured detached Test values. The raised toolbar and terminal dock retain native mouse input and compact layouts. Output preserves full errors and debugger terminal lines for copying.

Line numbers use measured glyph height plus line spacing, text insets and wrapped logical-line heights in both editor providers. The Integrations line-number preference applies to all source panes and removes gutter width when hidden.


Functions metadata places an editable namespace combobox before Name. Suggestions use the shared flat selector, show existing namespaces on focus and filter while typing; a valid new namespace remains ordinary staged text. Stable registry IDs remain internal rather than occupying the form.

Arguments and Returns are collapsible ordered collections using the same rounded row, arrows, drag presentation and gap targets as other editors. Their right-aligned + controls append when clicked or insert where dropped. Saved-function reorder uses a confirmation because positional callers may break; cancellation and stale callbacks do not change the array. Argument order changes compiled parameter order, while return order is documentation and requires manual review of Lua return statements. New drafts have no saved callers and reorder directly. Bindings shares the code action row immediately before Check syntax. Longer invocation and multiple-result guidance stays in Help.

Committed signature changes remeasure only the signature and adjust existing code geometry when its height changes. They preserve source, caret and provider ownership; unchanged updates do not repeatedly reflow the editor.


Test and render-preview roots are attached directly to the native scroll frame, so they must be explicitly shown on every acquisition. AceGUI releases hide pooled root frames; reparenting does not show them again. The integration regression uses shipped AceGUI containers/layouts and the actual Attackable and Allies callbacks across repeated Test/preview opening.

Advanced Run/Debug actions stay clickable when Test values are missing and explain the prerequisite in the visible editor status and hover text. Execution still enforces configured Test values. Status occupies a reserved strip below code and the debugger dock. A successful Fields UI/Help Run shows its detached render preview without automatically opening a second Output dialog; errors remain available in a copyable output window.

Argument and return metadata rows use a compact Type/Name/Nullable line at normal widths, responsive wrapping at narrow widths, and Help/Duplicate/Delete on the right. Saved-signature warnings cover reordering and insertion before an existing position; end-appends and unpublished drafts preserve the prior warning policy. Title dragging belongs to shared dialog chrome, so themed child windows retain native field editing while moving through their title bars.
