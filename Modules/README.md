# Packaged rotations

## Module layout

Built In packs are not part of the main addon. Each class is its own load-on-demand addon, `Modules/RotationMaster_<Class>/` (`DeathKnight`, `DemonHunter`, `Druid`, `Evoker`, `Hunter`, `Mage`, `Monk`, `Paladin`, `Priest`, `Rogue`, `Shaman`, `Warlock`, `Warrior`): 13 modules, each holding

- one folder per edition with premades for that class: `era/` (Classic Era and Season of Discovery), `tbc/`, `forever/`, `retail/`, each with the class's shared Built In blocks (`blocks.lua`) and one file per pack;
- one client-flavor TOC per such edition, `RotationMaster_<Class>_<Flavor>.toc`, with `## LoadOnDemand: 1`, `## Dependencies: RotationMaster`, that edition's `## Interface`, then `bind.lua` and only that edition's folder (blocks first, then the packs in order): `_Vanilla` (Classic Era 1.15, 11509), `_TBC` (TBC Anniversary, 20506), `_Camelot` and an identical `_Forever` (WoW Forever, 16001), `_Standard` (Retail/Midnight, 120105);
- `RotationMaster_<Class>.toc`, the unsuffixed fallback every other client reads: it loads nothing, so a client whose edition has no premades for the class (or one the module does not recognize) gets no packs rather than every edition's;
- `bind.lua`, identical in every module.

The client picks the TOC itself (Warcraft Wiki, "TOC format"): a suffix naming its game type first, then its family suffix (`_Mainline`, `_Classic`), then the unsuffixed file. Forever's game type is `camelot`, with `forever` listed as its alias (the wiki notes Camelot may be renamed Forever), so both are shipped; Retail uses `_Standard` (added in 12.1.5) rather than `_Mainline`, because the Mainline family also matches Forever.

At startup, just before the rotation library builds its catalog, `Core/builtin_modules.lua` (`addon:LoadBuiltInModule`) reads the player's class and asks the client for exactly `RotationMaster_<Class>` with `C_AddOns.LoadAddOn` (or the global `LoadAddOn` on old clients). No other class's module is parsed, and inside it only the client's edition runs. If the module is missing, disabled or fails to load, Rotation Master keeps working without Built Ins and prints one message naming the module and the client's reason. `notForThisCharacter` in `Core/rotation_library.lua` still drops another edition's or class's pack, as a safety net and for the offline tools that set `loadAllDefaults`.

A load-on-demand addon's files receive the module's own name and a fresh private namespace, not Rotation Master's. `bind.lua` hands that namespace to the fixed global `RotationMasterBuiltIns.Bind`, which gives it exactly `RegisterDefaultBlock` and `RegisterDefaultRotation`, forwarded to Rotation Master. Pack and block sources therefore keep `local _,addon=...` and call `addon:Register…` unchanged; they may use nothing else from Rotation Master. (Older source comments still name a pack's shared blocks by their pre-module path, `Defaults/blocks/<file>.lua`; that is now the same edition folder's `blocks.lua`.)

Adding a pack: put the file in `Modules/RotationMaster_<Class>/<edition>/` and add it to that edition's flavor TOC(s) after `blocks.lua` (both `_Camelot` and `_Forever` for Forever; they must stay identical). Adding an edition to a class (for example Classic Era or Mists): add its folder and its flavor TOC (`_Vanilla`, `_Mists`, …), and its row (family, folder, flavors) in `addon.BuiltInModules.editions` in `Core/builtin_modules.lua` so the offline tools find it. `tests/verify.py` fails when a module file is listed by no edition's TOC or by two, when a flavor TOC lists another edition's folder, when an edition's flavor TOCs differ, when the fallback TOC loads anything, when a TOC is not load-on-demand or does not load `bind.lua` first, when a pack sits outside a module, or when `.pkgmeta` does not move a module out; `tests/builtin_modules.lua` checks that every file in an edition registers only that edition and class. `python3 tools/generate_artwork_catalog.py --write` keeps the `.pkgmeta` `move-folders` lines that put each module in the release zip as its own top-level AddOns folder beside `RotationMaster`. Offline tools and tests find packs through `tools/builtin_modules.lua`, never through `RotationMaster.toc`.

A development install (a checkout linked into `Interface/AddOns`) needs one more link per module, since the client only scans top-level AddOns folders: `Interface/AddOns/RotationMaster_Shaman -> <checkout>/Modules/RotationMaster_Shaman`, and so on for all 13 (each carries every edition).

`Modules/RotationMaster_HelpText/`, `_ConditionText/`, `_DiagnosticsText/` and `_IntegrationsText/` are not classes either: each is a load-on-demand add-on that holds only translations (the English and the ten languages of a block of text nothing reads while the game is loading), with a single TOC and no Lua but `enUS.lua` and the ten locale files. `tests/verify.py` treats a module whose fallback TOC lists files that way (one TOC, every Lua file listed exactly once, no flavor TOCs, no `bind.lua`). `Core/text_bundles.lua` loads one the first time a key it owns is read; `Locales/bundles.json` lists them, `tools/locales.py` writes their files and `Data/text_bundle_index.lua`, and `docs/dev/architecture.md` ("Text bundles") explains the design. Never edit their locale files by hand. A development install links them too, one link each.

## Authoring

Definitions in this folder are addon data and read-only in game. They appear in the declared class’s list, including disabled and otherwise inapplicable definitions for that class. Explicit Universal definitions are shared. Enable preferences live in the profile's `rotationLibrary.preferences`. Clone creates an independent per-spec custom body in the existing SavedVariables rotation store; `rotationLibrary.origins` keeps its manifest, source revision, baseline and step origins. The default is never copied into that editable store automatically. Editing a clone cannot alter its source. Changing profiles rebinds preferences; no source pack overwrites saved rotations or the user's existing fallback.

Authoring requirements: version 1 envelope, stable pack ID/revision and step IDs, explicit edition/action context, localized name/description keys, provenance and independent condition tables. Packaged definitions declare a class or explicitly declare Universal applicability; specialization may be omitted. Unknown condition/schema/edition data remains visible but unavailable for execution. Roles and intent selectors currently remain reference-only until their context providers are implemented; do not silently treat them as universal. `rulesets` selects by season and game rules from the build context: any listed token that is active matches (`standard`, `hardcore`, `self-found`, `season:<id>`, `season:<seasonname>`, `mode:<id>`). `minExpansion`/`maxExpansion` (integers from 0, inclusive, either may be omitted) select by the client's expansion, `LE_EXPANSION_LEVEL_CURRENT`: 0 Classic Era, 1 TBC, 2 Wrath, 3 Cataclysm, 4 Mists of Pandaria. `minBuild`/`maxBuild` cannot do this, because Blizzard numbers builds across all its products (on 2026-10-21/22 Era was 70003, Titan-Reforged Wrath 70522, Retail 70529 and MoP 70531), so a Wrath client can carry a higher build than MoP. Every pack written for one expansion inside a shared family declares it: a Mists of Pandaria Classic premade is `families={'progression'},minExpansion=4,maxExpansion=4`. Such a pack is never registered on a character whose client reports another expansion, and is ineligible (`expansion-mismatch`, or `missing-expansion` when the client reports none) wherever it is loaded anyway. Packs for a vehicle, possession, override bar or pet battle declare that `actionContext`; they are chosen only while that bar is up and may reference gear through the `SET_PIECES`, `EQUIPPED` and `WEAPON_IMBUE` conditions. Retail/Forever defaults remain reference-only under the current restricted-data policy.

Shipped premades declare in `applicability` only what cannot change in a session: `families`, `class`, `actionContext`, `minExpansion`/`maxExpansion`, `minBuild`/`maxBuild` and `rulesets`. Level and specialization change mid-session (a level-up, a respec), so neither is applicability. A premade's specializations are its own property, `body.specs` (a list of specialization IDs; absent means any): it is listed, offered by the minimap menu and `/rm set`, and tried by automatic switching only while the character plays one of them, and a premade with nothing else to test has no switch at all: no switch condition matches whenever its specializations, level and edition allow it (priority ranks it), so an always-true switch such as `LEVEL >= 1` would only be noise. Only Retail and Mists of Pandaria Classic premades declare `body.specs`: everywhere else a specialization value is a talent group (Platform/specializations.lua `GetRotationSpecKind`), which a premade cannot know. `tests/premade_style.lua` forbids `SPECIALIZATION` at the top of any shipped switch, and a switch that is always true. Level stays a visible switch condition (`LEVEL`, and on talent-tree clients `PRIMARY_TALENT_TREE`/`TALENT_TREE_POINTS` describe talents, which are not a talent group), cheapest and most decisive first, with `LEVEL >= 10` ahead of a check that is unavailable before talents; a bound that always holds (level 1, the edition's cap, a class's starting level) is left out, and so is a switch that would be only that: a premade with no other condition ships no switch. The auto-switch re-reads them, so the right premade takes over without a reload. `applicability.specs`/`minLevel`/`maxLevel` remain honored for imported or older packs. Rotations are efficient: never two consecutive Stops where one Stop with an OR of their conditions does the same job (also across blocks in the composed pack: a block variant or a shared boundaries block takes the extra condition), and never two consecutive Branches with the same arms; `tests/premade_style.lua` enforces both. OR evaluates its children in order and stops at the first that matches or is unavailable, so one Stop on OR(c1..cn) behaves exactly like consecutive Stops on c1..cn, unavailable included.

**Names.** A Built In's display name (`Default.<Edition>.<Class>.<Pack>.Name` in `Locales/enUS.lua`) keeps only what tells the premade apart from its siblings: the variant, source or approach (`Blizzard Assisted with brews`, `Reference (Icy Veins)`, `Bite only in execute (Icy Veins)`). It never repeats what the list row, the minimap and the website already show or the player already knows: not the class, not the edition, no `Class:` prefix, and not a specialization the pack declares in `body.specs`. A pack that declares none (every Classic Era, Season of Discovery, TBC and Forever pack, the Mists "before a specialization" packs and the Mists Unholy Death Knight) keeps the role or build it is for (`Ranged`, `Tank`, `Unholy`), because nothing else says it. Season of Discovery packs keep `SoD` (`Balance (SoD)`), because the Classic Era packs load there as well. Sources go in parentheses after the approach; a reference-only premade says `reference`; the main premade of a specialization with nothing to add is `Recommended`. A name is never empty, starts with a capital and has no trailing punctuation, and is unique within its class, load scope and specialization; if two collide, add the smallest distinguishing word from the old name (a source, `reference`), never the class, specialization or edition. The identifier (`brewmaster-guide`) comes from the pack id and does not change with the name; copies a player made keep their own names. `tools/builtin_names.py` derives the names from the old ones (`apply`), checks them (`check`, part of `tools/check --static`) and writes `docs/builtin-name-changes.md` (`docs`), the before and after of every pack; `tests/builtin_names.lua` enforces the rule on the shipped packs. Names are translated text: change one and retranslate it in the other ten locales.

Run `python3 tools/check`. Class scenario suites such as `tests/defaults_tbc_shaman.lua` load real predicates and the shipped packs and exercise switches, priorities, Stops and upkeep. The shared native roster/editor now shows packaged and custom definitions with the same read-only/editable card layout.

`tests/default_corpus.lua` automatically loads every block and pack file the module TOCs list (`tools/builtin_modules.lua`) across five synthetic client families (progression twice: a Mists client, expansion 4, and a Wrath client, expansion 2) and thirteen class tokens. It checks source/review metadata, English name/description coverage, schema resolution on matching editions/classes, nested stable IDs, definition validation, visibility, read-only isolation, enable/disable and runtime exclusion at sampled level/spec/build/context boundaries. Invalid-manifest probes verify the guard rejects missing translations/sources, invalid dates and incomplete conditions/branches. It never evaluates combat conditions. This is an authoring/selection gate; it adds neither class coverage nor gameplay scenarios, and synthetic declarations do not certify live APIs or recommendation quality. Add pack-specific behavioral scenarios alongside new packs.

Default, clone and import validation share effective global/profile item-set references, with a nonnil profile entry taking precedence. Dependency additions/removals and registered schema changes refresh catalog validation without reload; unchanged lookups do not revalidate all packaged graphs. A structurally valid packaged source remains visible with diagnostics if a changed condition schema makes it invalid. Runtime eligibility keeps that source inert; custom saves still use strict current-schema validation. Extensions should change schemas through RegisterCondition/UnregisterCondition rather than silently mutating nested fields.

A shared leveling pack is appropriate when removing unavailable spells from its later-level priorities leaves the correct early priority order. A change in relative order due to talents or mechanics requires an explicit conditional branch or a distinct automatically selected pack; spell availability alone must not be assumed to prove equivalence.

## Built In composition

Packaged definitions can share named step blocks; this is authoring-time reuse only. `RegisterDefaultRotation` expands every reference once, at load, so the catalog, editor, runtime, export and Clone only ever see a fully expanded independent tree. A clone copies every included step, and neither later block edits nor clone edits reach the other. Users cannot see or author a block.

Put a class's blocks for an edition in that edition folder's `blocks.lua`, listed in its flavor TOC after `bind.lua` and before every consumer:

```lua
assert(addon:RegisterDefaultBlock({id='shared.preserve-cast',revision=1,families={'era','tbc'},class='ROGUE', -- class optional
 steps={{id='cast',type='stop',suppress_attack=true,conditions={type='CASTING',unit='player'}}},
 overrides={{families={'tbc'},steps={...}}}}))  -- optional whole-variant replacements by families and/or specs
```

A consumer pins every block it reaches, including nested ones, in `blocks`. It references a block as a step anywhere in `rotation`, `cooldowns`, a branch arm or another block:

```lua
id='rm.tbc.rogue.dps.wowsims',revision=1,blocks={['tbc.rogue.opening']=1,['tbc.rogue.upkeep']=1,['tbc.rogue.builders']=1},
rotation={{id='rogue-ref-opening',type='block',block='tbc.rogue.opening',prefix='rogue-'}, ...}
```

An expanded step ID is the reference's `prefix` (default `<reference id>.`) followed by the block step's ID. Prefixes compound through nested references, so IDs stay stable across reloads and differ per inclusion. Choose a prefix that keeps existing IDs when converting a shipped pack, since saved clones' step origins name them. `families` lists every edition the block was reviewed for. TBC may share Classic blocks only after reviewing changed talents and mechanics; shared spell names alone are insufficient. An override replaces the whole step list, and applies only when the consumer's whole edition/spec scope lies inside its selector; a partial match or a second matching override is rejected. Expansion also hard-rejects missing or undeclared blocks, unused or stale pins, cycles, duplicate block or expanded IDs, and incompatible editions or classes. Each rejection names the failing location.

A block content change needs a new block revision. Every consumer's pin must then change, or it fails to load. Bump the consumer's own revision too. Record both as new rows in `tests/fixtures/builtin_composition_ledger.lua`; `tests/builtin_composition.lua` fails when content or pins change without a revision bump. A block change therefore always reaches clones as a source revision with a source-side diff. `rm.tbc.rogue.starter.30-39` and `.40-49` share `Modules/RotationMaster_Rogue/tbc/blocks.lua` and expand to their exact pre-composition trees.

## WoW Forever premades

`Modules/RotationMaster_<Class>/forever/<class>-<role>.lua` (ids `rm.forever.<class>.<role>[.<source>]`) with shared blocks in `Modules/RotationMaster_<Class>/forever/blocks.lua`, levels 1–60 (talent-gated roles from 10), `families={'forever'}`, for Druid, Hunter, Mage, Paladin, Priest, Rogue, Shaman, Warlock and Warrior. Forever has one specialization ID per class; its three classic talent trees are trait node groups, which `TALENT_TREE_POINTS` and `PRIMARY_TALENT_TREE` read (`Platform/talents.lua`), so role switches use the tree points and main tree where the guides tie a role to a tree, and known-spell or own-aura proxies elsewhere (for example Pyroblast for Fire, Strider Kick for Survival, Holy Shock plus a group for a Holy Paladin, Defensive Stance for a Warrior tank); talent spells are matched across all their rank IDs, and the catch-all premade of each class has the lowest priority. Player-chosen source variants share their recommended sibling's switch at a lower priority and ship disabled ("off by default: enable it and disable that one, or raise its priority"), so the recommended premade is the one that auto-selects. RM classes Forever as `combatDataPolicy="restricted"`: health, mana, every primary power (rage, energy) and the target's mana are secret there, and the combat log, which time-to-die forecasts and swing timers need, is not available to addons (`docs/restricted-clients.md`). No Forever premade uses those conditions, so every one is complete and the recommended premade auto-selects like on any other client. What that costs is stated in each description: no execute windows except spells the client itself only allows in range (Execute, Hammer of Wrath), no will-it-live checks for DoTs and totems, no mana or rage thresholds (an unaffordable spell is simply not ready, so wands and melee take over), no health-triggered heals or emergency buttons (Lay on Hands, Ice Block, Last Stand, Life Tap, Mend Pet and Health Funnel are the player's), and healers act on the friendly target the player picks without judging how hurt it is. Conditions that are only momentarily secret (auras and cooldown times in combat) stay: a step that cannot read them is skipped, a Branch or Stop pauses for that poll. `tests/defaults_forever_<class>.lua` exercise the packs on a synthetic Forever context with `probe` policy (shared models: `tests/fixtures/forever_premade_model.lua` and `tests/fixtures/forever_rogue_shaman_warlock_warrior.lua`) and check on the real restricted context that every premade is complete and the right one auto-selects. Branch and Stop conditions use observations that do not routinely go unavailable: enemy counts in branches are engaged enemies (`THREAT_COUNT`), player-centered `DISTANCE_COUNT` appears only inside single steps, "the target is attacking you" is your threat on it (`THREAT`; `ISSAME` on `targettarget` is a compound unit token and always secret on restricted clients), and combo points are read on the player as on Mainline-engine clients. Every guide behind them is a level-30 beta guide; spell IDs follow the research's Wowhead and SimulationCraft cross-check and still need in-game verification.

## Retail premades: Death Knight, Demon Hunter, Druid, Evoker, Hunter, Mage, Monk

`Modules/RotationMaster_<Class>/retail/<class>-<spec>[-<source>].lua` (ids `rm.retail.<class>.<spec>[.<source>]`) with shared blocks in `Modules/RotationMaster_<Class>/retail/blocks.lua`, `families={'retail'}`, levels 10–90 (8–90 for Death Knights and Demon Hunters). Each premade declares `body.specs={<spec ID>}` with the always-true switch `LEVEL >= 1`, so it is listed and chosen in that specialization only (see Authoring: specialization is the premade's own property, level lives in the switch). In Midnight combat most data an addon reads is secret (buffs, debuffs, cooldown times, primary resources, health, enemy casts), so the recommended premade for every damage and tank spec is **Blizzard Assisted** (bare id, priority 20): stop while casting or channeling, then one `assisted` step ("Blizzard's suggestion", `docs/assisted-combat.md`), plus independent highlights for what Assisted Combat never suggests — the cooldowns SimulationCraft's model marks as outside it or lists separately (Breath of Sindragosa, Metamorphosis, Celestial Alignment, Berserk, Trueshot, Takedown, Arcane Surge, Combustion, Zenith, Celestial Conduit…), tank mitigation, defensive cooldowns and racials (in combat, decided by the readable cooldown flags: health is secret on Retail, so a defensive is a reminder whenever it is ready, and emergency buttons such as Ice Block, Lay on Hands or Crimson Vial are left to the player), and interrupts on an interruptible cast (lit only where the enemy cast is readable). Guide lists (Icy Veins, Wowhead, SimulationCraft `default`) are reference premades shipped `disabled` (`.guide` priority 10, extra `.simc`/`.wowhead` sources 5): they keep the guides' aura and cooldown logic, which Midnight hides in combat (those steps are skipped there), and drop what is always secret: health, primary power and execute windows by target health become spending at a spell's cost (an unaffordable spell is not ready) or are left out, as each description says. Exceptions follow the research: Augmentation's Icy Veins Ebon Might list is the recommended premade (Ebon Might is a whitelisted aura) with Assisted as a disabled alternative; Brewmaster's Assisted premade adds Icy Veins' brews; Restoration Druid uses the Assisted step on an enemy and maintenance heals on a friend; Preservation and Mistweaver are reference-only. RM classes Retail as `combatDataPolicy="restricted"`; no Retail premade uses a condition that is always secret there (health, mana, primary power, the combat log), so every one is complete and the recommended premade auto-selects in its specialization slot. `tests/defaults_retail_<class>.lua` exercise them on a synthetic Retail context with `probe` policy and a modeled `C_AssistedCombat` (shared model: `tests/fixtures/retail_premade_model_a.lua`), including a Midnight-secrets scenario, and check on the real restricted context that every premade is complete and the recommended one auto-selects. Spell IDs follow the research and the SimulationCraft 12.1.5 spell dump and still need in-game verification.

### Retail before a specialization

A Retail character who has not chosen a specialization (new characters start without one) has "No specialization": the game reports the class's initial specialization (Blizzard's ChrSpecialization data, order index 4: Warrior 1446, Paladin 1451, Hunter 1448, Rogue 1453, Priest 1452, Death Knight 1455, Shaman 1444, Mage 1449, Warlock 1454, Monk 1450, Druid 1447, Demon Hunter 1456, Evoker 1465). Every Retail class has one premade for that slot, `rm.retail.<class>.initial` (`<class>-initial.lua`, `body.specs={<initial spec>}` and the always-true switch `LEVEL >= 1`, so it is chosen whenever the character has no specialization, at any level): the class's boundary Stops (one Stop on a cast or channel, and no attackable target where that class stops on it), then Blizzard's Assisted Combat suggestion, with the class's shared reminders alongside. The class test suites check that a level-4 character in the initial specialization gets it auto-selected and complete on the restricted client.

Blizzard's Assisted Combat has no list for the healer specializations (Holy Paladin, Discipline, Holy Priest, Restoration Shaman, Preservation, Mistweaver; the research's SimulationCraft model covers none of them), so those slots keep their readable-input healer premades (Preservation and Mistweaver only a disabled reference) and have no Blizzard Assisted premade.
